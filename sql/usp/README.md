# Интеграция мобилки с УСП

## Координаты базы

| Что | Значение |
|---|---|
| REST / Auth / Storage | `http://91.147.81.4:8080` |
| Фронтенд УСП | `http://91.147.81.4:9001` — **не API**, отдаёт `index.html` на любой путь |
| Схема данных УСП | `erp` (не `public`) |
| Схема данных мобилки | `mobile` |
| Открытые схемы PostgREST | `public, erp, warehouse, graphql_public` — `mobile` нужно добавить |

Обращение к схеме из supabase-js: `supabase.schema('erp').from('contract_assignments')`.
Через curl — заголовок `Accept-Profile: erp` (для чтения) и `Content-Profile: erp` (для записи).

## Порядок применения

1. `01_mobile_schema.sql` — схема `mobile`, 18 таблиц, связка `contractor_users`, триггеры `updated_at`.
2. **Открыть схему в PostgREST** (иначе таблицы не видны через API):
   ```yaml
   PGRST_DB_SCHEMAS: "public,erp,warehouse,mobile,graphql_public"
   ```
   перезапустить контейнер `rest`. Проверка:
   ```
   curl "http://91.147.81.4:8080/rest/v1/reports?select=id&limit=1" \
     -H "apikey: $ANON" -H "Accept-Profile: mobile"
   ```
   Должно вернуться `[]`, а не `PGRST106 Invalid schema`.
3. `02_mobile_rls.sql` — RLS и права.
4. `03_mobile_views.sql` — витрина чтения: работы договоров и ресурсы по ним.
   **Применять только под `postgres`** — см. ниже.
5. `04_mobile_registration.sql` — регистрация из мобилки и привязка к
   контрагенту. Тоже под `postgres`.
6. `05_mobile_approval.sql` — подтверждение доступа администратором. Под
   `postgres`.
7. `06_fix_profiles_role_check.sql` — расширяет `profiles_role_check` ролями
   мобилки. **Без него регистрация не работает вовсе**: `register_profile`
   падает с 23514 на любой роли из формы. Выполнять по одному блоку, под
   `postgres`.
8. `07_registration_hardening.sql` — валидация роли в `register_profile`,
   возврат фактической роли клиенту, диагностика и досоздание профилей у
   пользователей, которые остались без них. Блоки 2–4 разовые: выполнять по
   одному и смотреть на результат. Под `postgres`.
9. `08_lock_legacy_access_keys.sql` — необязательная уборка: снимает с
   легаси-таблицы `public.access_keys` политику, открывавшую её на запись
   любому вошедшему. Таблицу не использует ни приложение, ни бэкенд УСП.
10. `09_bootstrap_admin.sql` — назначает администраторов по email. **Без
    этого шага заявки на доступ подтвердить некому**: `mobile.is_admin()`
    возвращает false, раздел «Ещё → Управление доступом» не появляется, и
    заявки лежат в `mobile.contractor_users` со статусом `PENDING`. Список
    адресов задаётся в файле. Под `postgres`.
11. `10_cleanup_orphan_links.sql` — убирает заявки на привязку, у которых
    больше нет пользователя в `auth.users`, и перестаёт показывать такие
    строки в `admin_list_links`. Иначе счётчик ожидающих заявок у
    администратора невозможно обнулить. Под `postgres`.

После `07` не применяйте `04_mobile_registration.sql` повторно: у
`register_profile` изменился тип возврата, и `create or replace` завершится
ошибкой «cannot change return type of existing function».

## Где хранится пользователь

Регистрация раскладывает данные по трём местам:

| Что | Куда | Кто пишет |
|---|---|---|
| Учётная запись, метаданные, `display_name` | `auth.users` | бэкенд УСП, `admin.createUser` |
| ФИО и роль | `erp.profiles` | бэкенд УСП, тем же запросом |
| Привязка к контрагенту | `mobile.contractor_users`, `status='PENDING'` | приложение, `mobile.link_contractor` |

Профиль заводит **бэкенд**, а не приложение: транзакции между Auth и БД нет,
и пока профиль писал клиент отдельным запросом после отдельного входа, любой
сбой между шагами оставлял пользователя в `auth.users` без профиля — повторная
регистрация падала с «email already registered». Если профиль не записался,
`registerMobile` удаляет только что созданного auth-пользователя.
`mobile.register_profile` остался страховкой для аккаунтов, заведённых не
приложением (панель Supabase, веб-ERP), — его вызывает `fetchProfile`.

## Назначение администратора

Признак администратора хранится в `mobile.app_admins`, а не в `erp.profiles.role`:
набор значений `role` задаёт УСП, он может измениться без нашего ведома, и
завязка на него однажды тихо раздала бы права всем подряд.

```sql
insert into mobile.app_admins (profile_id, note)
values ('<uuid пользователя из auth.users>', 'ФИО');
```

После этого в приложении, в разделе «Ещё», появляется «Управление доступом».

## Подтверждение доступа

Заявка подрядчика (`mobile.link_contractor`) создаётся со статусом `PENDING` и
**не даёт ничего**, пока администратор её не подтвердит. Ограничение держится
на одной функции — `mobile.my_contractor_ids()` возвращает только `APPROVED`,
а на неё опираются все витрины и политики RLS.

| Функция администратора | Назначение |
|---|---|
| `admin_list_links(status)` | Заявки и действующие привязки |
| `admin_set_link_status(user, contractor, status, comment)` | Подтвердить / отклонить |
| `admin_assign_contractor(user, contractor)` | Назначить напрямую, минуя заявку |
| `admin_revoke_contractor(user, contractor)` | Отозвать доступ |
| `admin_list_contractors(search)` | Справочник организаций |
| `admin_list_users(search)` | Пользователи приложения |

Каждая начинается с проверки `is_admin()`: функции `security definer`
выполняются с правами `postgres`, и без явной проверки любой авторизованный
пользователь получил бы полный доступ к чужим заявкам. Скрытый пункт меню в
приложении защитой не считается.

## Регистрация подрядчика из мобилки

Прямые запросы невозможны: `erp.profiles` и `erp.contractors` закрыты RLS, а
`insert` в `mobile.contractor_users` отозван у `authenticated` намеренно —
иначе прораб приписал бы себя к любому контрагенту. Всё идёт через RPC:

| Функция | Назначение |
|---|---|
| `mobile.register_profile(first, last, role)` | Заводит строку в `erp.profiles`. Идемпотентна, `role` при повторе не перезаписывается. |
| `mobile.link_contractor(uuid, bin)` | Привязывает пользователя к контрагенту. |
| `mobile.my_contractor()` | Своя организация + счётчики договоров и работ. |
| `mobile.my_profile()` | Свой профиль. |

**Идентификатор контрагента — это ключ доступа.** Кто его знает, тот получает
работы всех договоров компании. Угадать UUID нельзя, но утечь он может,
поэтому при заполненном `contractors.bin_iin` функция требует и БИН. Если БИН
в карточке пуст, проверять нечего — привязка проходит по одному ID.

Если такой модели окажется мало, следующий шаг — флаг подтверждения в
`contractor_users`, который включает администратор УСП.

Все три файла проверены на локальном Postgres 17 с воспроизведением боевой
картины (RLS включена на `erp.contracts`, `erp.contractors`,
`erp.contract_assignments`). Проверено: прямое чтение `erp` под прорабом даёт
ноль, витрина отдаёт только его работы, непривязанный пользователь не видит
ничего, запись в чужую работу и самоприписка к чужому контрагенту отклоняются.

## Почему чтение идёт через представления

На `erp.contracts`, `erp.contractors`, `erp.contract_assignments`, `erp.profiles`,
`erp.organizations` включена RLS командой УСП. Добавлять туда свои политики —
лезть в чужой контур и рисковать их фронтендом.

Вместо этого мобилка читает `mobile.v_assignments` / `v_assignment_resources` /
`v_objects`. Представление принадлежит `postgres` и выполняется с его правами
(`security_invoker` НЕ включаем), поэтому RLS таблиц `erp` обходится, а
единственным фильтром остаётся условие по `mobile.contractor_users`.

Отсюда требование: `03_mobile_views.sql` применяет суперпользователь. Если
владельцем представления окажется обычная роль, RLS не будет обойдена и прораб
увидит пустой список.

## Расхождения со `docs/СТРУКТУРА.txt`

Проверено на живых данных, документ в этих местах неточен:

1. **Локализация связана через `object_id`, а не `name_id`.** В доке
   `jobs_cas.name_id → localization.id`. На деле искать надо так:
   ```sql
   select name from erp.localization
   where object_name = 'jobs_cas' and object_id = <id работы> and locale = 'ru'
   ```
2. **Живые справочники — `*_cas`.** `est_doc_works.work_id → jobs_cas.id`,
   `est_doc_resources.resource_id → Materials_cas.id`. Таблицы `jobs` и
   `resources` заполнены, но смета на них не ссылается.

## Согласованные договоры и фактические сметы (миграция 11)

Перед публикацией клиента со схемой 11 выполнить
`11_approved_actual_assignments.sql` в SQL-редакторе от владельца витрин
`mobile` (postgres). Скрипт выполняется в транзакции, повторный запуск допустим.
Старый клиент совместим с обновлёнными витринами, поэтому сначала обновляется база.

- Только `contracts.status = 'APPROVED'` и `est_documents.estimate_type = 'actual'`.
  `ACTIVE`, `REVISION` и ожидание согласования не подходят.
- Связь через UUID строки сметы; плановые строки автоматически не заменяются.
- Объём работы: `fact_volume ?? volume`; норма: `fact_norm ?? norm`.
  Нулевой факт сохраняется. `assigned_quantity` остаётся объёмом по договору.
- После полной загрузки недоступные задания скрываются локально, ссылки старых
  отчётов сохраняются. При ошибке загрузки неполный снимок не применяется.
- Первый запуск новой схемы требует успешной синхронизации. Дальше офлайн
  доступна последняя проверенная выдача. Перед отправкой проверка повторяется;
  серверные политики запрещают запись отчёта по недоступному заданию.
- Складские остатки не берутся из количества ресурсов сметы.

Проверка: `node scripts/test-assignment-policy.cjs` и `npx tsc --noEmit`.
После применения SQL проверить под обычным пользователем `mobile.v_assignments`:
все строки должны иметь `contract_status = APPROVED`, `estimate_type = actual`,
а `estimate_doc_id` должен вести к фактической смете. Отмена согласования должна
убирать задание после синхронизации, не удаляя его старые отчёты.

## Что ещё не сделано на стороне УСП

- **TLS.** База отдаётся по HTTP. Android (API 28+) и iOS ATS режут cleartext —
  для боевой сборки нужен сертификат, послабления в `app.json` не вариант.
- **RLS на схеме `erp`.** Сейчас анонимный ключ читает сметы и справочники
  целиком. Мобилка ограничивает выборку на клиенте, но это не защита —
  решение за командой УСП.
